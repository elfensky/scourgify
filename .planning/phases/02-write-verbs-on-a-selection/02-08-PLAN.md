**(a) `def failure_groups(rows, env=None)` in `plugin/jobs.py`** — the shared derivation both retry
surfaces read, so the dialog and the menu cannot disagree about what is retryable. Given failure rows
(`[{book_id, title, reason}, ...]`), return a plain list of groups, one per class present. Each group
is a dict with keys `cls` (one of `engines.CLASSES`), `books` (a list of ints), `titles` (a
book-to-title mapping), and `targets` (a list of dicts with keys `engine`, `cost` and `label`).

The `targets` list is what decides which controls exist, and it comes from the taxonomy, never from
a name test:

  - class `refusal` → one target per usable engine OTHER than the one that refused. A refusal is
    deterministic content policy, so a different engine is the recovery.
  - a class in `engines.RETRYABLE` → exactly one target: the SAME engine, because a quota, timeout,
    parse or transient error is answered by trying again.
  - `auth` and `permission` → NO targets. Retrying a bad key elsewhere is the same failure plus a
    wasted click, and offering the control would be a lie about what it can fix.

Each target's `label` is built from `classify.est_cost(len(books), engine)` through the SAME
sub-cent-aware price fragment `engines.engine_options` uses (plan 02-03 task 1a) — reuse that
helper rather than formatting a price here, so one rounding rule exists in the codebase. A free
on-device engine's label says free.

**(b) `def job_retry_classify(lib_path, lib_uuid, book_ids, engine_id, model, api, now_uuid=None,
abort=None, log=None, notifications=None)`** — the ONE retry entry point, called by the result
dialog's buttons AND by the menu slot. It is `job_execute_classify` restricted to an explicit id
list: build the plan with mode `ids` over `book_ids`, steer `p.opts.engine`/`model`/`yes` on the
resolved plan, run with the injected ask, and write through `_Writer(api, engine=engine_id,
model=model)`. It relies on the existing per-run failure-log rewrite, which is what keeps the log
finite: a book recovered on the retry leaves the log rather than accumulating a second row.

**(c) `def job_retry_targets(lib_path, lib_uuid, ids, now_uuid=None, abort=None, log=None,
notifications=None)`** — the read job the menu needs, because `build_menu` cannot call the core:
read the failure log, keep the rows whose book is in `ids` (or all rows at library scope), and
return `failure_groups(...)`. The action caches the result to grey or un-grey the
`Retry on another engine` slot, exactly as it caches the write-running and synopsis reasons.

**(d) Tests in `tests/test_plugin_jobs.py`**, engine reached through an injected ask so nothing is
sent: `failure_groups` yields other-engine targets for a refusal row, a same-engine target for each
retryable class, and NO targets for `auth` and `permission`; a group's label carries the sub-cent
price for a one-book group on a cloud engine and says free for the on-device engine; and running
`job_retry_classify` twice over the same books leaves at most one failure row per book, with a book
that succeeded on the second attempt absent from the log.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| engine failure reason → result dialog / menu label | an error string that may echo a key or untrusted response text |
| retry control → a billed engine run | a click that spends money |
| library metadata → Qt result table | untrusted titles and field values in rendered cells |
| worker thread → GUI thread | two concurrent results crossing the Dispatcher boundary |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-32 | Information Disclosure | a key echoed in a failure reason rendered in the dialog or a menu label | high | mitigate | Reasons reach the dialog only through the failure artifact, whose rows `ask_retry` already built via `engines.redact`; the dialog renders the stored reason and never formats a raw exception. |
| T-02-33 | Tampering | a retry offered for a class it cannot fix, causing repeated spend | medium | mitigate | Targets are derived from `engines.RETRYABLE` and the refusal rule in one helper: `auth` and `permission` get no control at all, a refusal gets other engines, a retryable class gets the same engine — so a control that exists can help. |
| T-02-34 | Repudiation | a run reported as fully written while books were skipped or failed | high | mitigate | The summary is built from the result's `skipped` and `engine_failures` lists, both required siblings of the write counts; the row table names each skipped and failed book individually. |
| T-02-35 | Information Disclosure | untrusted title or field text in a result table cell | low | mitigate | Plain-text rendering on every cell (ASVS L1 V5). |
| T-02-36 | Denial of Service | a menu left permanently greyed by a job that ended in an exception | medium | mitigate | The write-running flag is cleared in every wrapped completion including the failure path, asserted by a source count in this plan's acceptance criteria and exercised by the selftest's error path. |
| T-02-SC | Tampering | package-manager installs | low | accept | No external package is installed by this plan (02-RESEARCH.md `## Package Legitimacy Audit`: not applicable). Any future install re-enters the package-legitimacy gate. |
</threat_model>

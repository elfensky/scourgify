**(a) The two generic decide helpers in `plugin/jobs.py`.** D-02 splits one review across two jobs:
the PLAN job's callback records the items and answers `skip`; the EXECUTE job's callback replays the
reviewer's ticks. Because `_step_walk` calls the callback ONCE PER BOOK, both helpers are
sequence-aware:

  - `def _record_decide()` → returns `(callback, calls)` where `calls` is a list that grows one
    entry per invocation: `{'title': title, 'subtitle': subtitle, 'items': list(items)}`. The
    callback answers `([], list(range(len(items))), 'skip')` — nothing accepted, the walk continues
    to the next book, and the plan object it mutates is discarded by the PLAN job anyway.
  - `def _replay_decide(ticks)` → returns a callback that pops the next `(accepted_idx,
    rejected_idx, action)` triple from `ticks` in call order and returns it, falling back to
    `(list(range(len(items))), [], 'apply')` — accept everything — when `ticks` is exhausted. The
    one-click path passes an empty `ticks` list and therefore accepts everything, which is exactly
    D-02's "all ticked on the one-click path".

Document that these are the ONLY two places the plugin fabricates a decide answer, and that neither
narrows a change-set itself — the tool module does the narrowing, which is what keeps the reject log
and the overrides flow working for the plugin exactly as for the terminal.

**(b) Wire staleness's review** (the tracer left the summary-plus-Run path only): pass
`_record_decide()`'s callback into `staleness.step(status_label, rows, decide=...)` in
`job_plan_staleness` to harvest items for the picker, and pass `_replay_decide(ticks)` in
`job_execute_staleness` so the reviewer's ticks narrow the rows before `staleness.write`. Both
deterministic verbs now share one review mechanism.

**(c) `def job_plan_wrangle(lib_path, lib_uuid, ids, now_uuid=None, abort=None, log=None,
notifications=None)`.** Load the config and maps (`common.load_config()`, `wrangle.load_maps(...)`),
build `p = wrangle.plan(cfg, m).restrict(ids)`, then in this order:

  1. Read the summary numbers off the plan before any walk: per-column change counts from
     `p.changes`, and the SAFETY line built from `p.lostF`, `p.lostC`, `p.tagsB`, `p.tagsA` in the
     same wording `Plan.preview` prints — put it on the result's `safety` key so the picker shows it
     above the Run button.
  2. Call `p.guard(force=False)` inside the ceremony so a data-loss-shaped change-set surfaces as a
     refused result carrying the guard's own sentence ("N book(s) would lose their last fandom …")
     and no dialog is opened for a run that cannot proceed.
  3. Harvest the review items with `p.step(decide=<recorder>)`, then flatten `calls` into the
     result's `items` list, preserving per-book grouping in each payload (`book`, `title`, `field`,
     `before`, `after`, `kind`, `class`) and preserving call order so the replay lines up.
  4. Return `plan_result` with the consequence label `Normalize fields on N books` and
     `carry = {'ids': list(ids), 'n_books': ...}`. When `p.changes` is empty return the D-04 empty
     result — this is also what makes a second identical run open no dialog, because the first run's
     write leaves nothing for `transform` to change.

The plan is discarded at the end of the PLAN job — a `Plan` object never crosses the Dispatcher
boundary. The EXECUTE job recomputes it; see task 2 for why that is the right trade here.

**(d) Tests in `tests/test_plugin_jobs.py`.** Against a `fixture_db` library with maps that produce a

**(a) `def job_execute_wrangle(lib_path, lib_uuid, ids, carry, ticks, api, now_uuid=None,
abort=None, log=None, notifications=None)`.** Recompute `p = wrangle.plan(cfg, m).restrict(carry['ids'])`,
`p.guard(force=False)`, then `p.step(decide=_replay_decide(ticks))` and
`p.write(write=_Writer(api))`. Build the EXECUTE result from the writer's `WriteResult`.

**Resolving the "no recompute" discretion note, on the record.** CONTEXT.md's Claude's Discretion
says the EXECUTE job should apply exactly the PLAN job's ops with no recompute. For wrangle this
plan deliberately recomputes, and records the reason in the SUMMARY: `_step_walk` is what writes the
reject rows to `data/rejects.csv` and what recomputes a book's net change when an individual edit is
unticked, and `Plan.write` is what builds each op's `expected` from `perbook`. Carrying an ops list
forward instead would move both of those into the plugin — a second place that assembles a write and
a second place that decides what a reject is, which is precisely the duplication CLAUDE.md's
"the wizard ASKS, the tool modules DO" rule exists to prevent. The recompute is deterministic over an
unchanged library, costs ~870 ms off the GUI thread (02-RESEARCH.md records this as a known accepted
cost matching `apply --books`), and any drift between the two computes is caught by the apply-time
conflict filter, which is the staleness net the discretion note names. Staleness keeps the
carry-forward shape (its rows carry their own before-values and it has no reject log), so both
shapes exist for a stated reason rather than by accident.

**(b) `plugin/action.py` — the live slot.** Turn `Normalize fields` live with the same greying rule
the tracer established: `'nothing selected'` on an empty selection, the running job's description
while `self._write_running` is set, else `None`. Its slot dispatches `jobs.job_plan_wrangle` through

immediately before and cleared in the wrapped completion. Reuse `_plan_done` / `_execute_done`
unchanged — a new verb must not need a new completion path.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| normalization rules (defaults + user overrides) → library write | an over-broad rule can empty a column across the library |
| reviewer's tick state → the write set | a deferred book must not be written and must not be logged as rejected |
| plugin job → live Calibre library handle | the wrangle write |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-02-18 | Tampering | an over-broad rule emptying a populated column | high | mitigate | `Plan.guard` runs in the PLAN job before any dialog opens and again before the write; its `GuardrailError` becomes a refused result carrying the guard's own sentence. The coarse wipe guard inside the shared pre-write protocol still runs underneath, unforced. |
| T-02-19 | Repudiation | a rejected edit leaving no override trail | medium | mitigate | The EXECUTE job replays ticks through `Plan.step`, so `_step_walk` writes the reject rows exactly as the terminal's `apply --step` does — the plugin adds no second definition of what a reject is. |
| T-02-20 | Tampering | a stale plan writing values computed against an older library state | medium | mitigate | The EXECUTE job recomputes the plan, and every op still carries a plan-time `expected`; the apply-time conflict filter skips and reports any book that drifted rather than clobbering it. |
